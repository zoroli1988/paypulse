02-A'加班两种口径：主账与影子账
计费加班统一 1.5×，不区分星期几
超出 7.5 小时的部分，按倍率真实计入今日已赚。
paid  = 日薪 + 单价 × 1.5 × 加班秒
shadow = 0（不生成）
悬浮窗表现：主数字继续上涨，状态徽章转蓝。
义务加班倍率 = 不计加班费
加班时段不产生任何收入，主账停在日薪值。但那段时间值多少钱，单独记一笔。
paid  = 日薪 （封顶，不再增长）
shadow = 单价 × 1.5 × 加班秒
悬浮窗表现：主数字停住但仍绿，另起一条琥珀色「今日白干」。
白干按 1.5× 折算。已定不做法定三档。 这里原先写的是「按法定倍率」——那是句错话。法定倍率不是一档，是三档：工作日 1.5×、休息日 2×、法定节假日 3×。

但真正的门槛不是那张节假日表（日历本来就有，见「作息与工作日」）。真正的门槛是： 要分档，先得知道「今天是什么日子」，而现在的计薪模型里根本没有这个维度—— 所有日子都按工作日算：日薪基线 367.82、9:00 开始累计、18:00 封顶。 休息日没有「下班」这个节点，也没有日薪基线，整个状态机要分叉： 周六整天按 2× 计、没有 base 段、没有「距下班」；法定节假日再一套。 这属于模型级改动，不是加一个常量。

代价必须写在明处：周末或法定节假日加班时，法定应得是 2× / 3×，这里只按 1.5× 折算， 数字会低于公司真正该给你的。所以界面措辞统一为「按 1.5× 折算的价值」， 不出现「公司应发」「法定应得」——它不是仲裁依据，只是一张让你看见损失的账。

连带的边界：既然模型不认休息日，休息日打开它，金额是虚的——它会照工作日给你涨到 367.82。 所以休息日默认自动暂停，悬浮窗显示「今天休息」，不产生任何数字。见 02-D「休息日与法定节假日」。

唯一的例外是午休加班：那里本来就不存在「加班费」这回事，套任何倍率都是虚构，所以只按 1× 时薪报「这段时间值多少钱」。
02-A″午休加班：一个按钮进出，白干单独记
午休加班现实里普遍没有加班费
午休时段本来就不计薪，所以这段时间被占用时，主账一分不加、也一分不减——它本来就还没到账。 真正被消耗的是休息本身，所以只记一笔「白干价值」。
paid   = 日薪 × 已计薪秒 / 27000 （午休期间恒定）
shadow += 单价 × 1.0 × min(加班秒, 13:30 − 开始时刻)
折算用 1×，不套 1.5×：加班倍率的前提是「这笔钱本该发给你」，而午休加班现实里普遍不给钱，套上去就是在虚构一笔收入。 这一栏要说清的是「这段时间值多少钱」，不是「公司欠你多少」——后者需要仲裁，前者只需要一张账。
两个必须守住的边界
① 封顶到 13:30。午休窗口一过，人就在正常工作时间里了，再记白干就是重复计算。 到点自动收口、切回在岗，不需要用户手动点。
② 一天可以开多段。白干按区间累加（[start,end] 毫秒集合）， 中途结束再开一段不会丢，也不会重复计。切到任何其它状态都会先结算当前区间。
这两条在数据库里就是 shadow_span 表的一行行记录，金额永远是这几行的纯函数，不是累加变量。
「结束加班」按当前时刻回到哪个状态
点「结束加班」的时刻回到为什么
午休中，离 13:30 还有时间午休中回去接着休，剩余分钟数接着走，不是从 12:00 重算
午休中，已经过了 13:30在岗午休窗口已结束，此刻本来就该在岗；白干按窗口封顶结算
下班后义务加班已下班结算终值不变，白干金额与时长保留在今日，不随状态消失
计费加班中已下班停止按倍率累加，主账锁定在已赚金额
按钮出现在哪些状态：午休中、已下班 → 「我在加班」；计费加班中、义务加班中 → 「结束加班」。其余状态（在岗、请假）不显示，避免误触。 紧凑态默认不显示动作行——那个尺寸只留数字，要操作就双击展开，这条在设置里可以放开。

✕ 错误做法：定时累加90% 的同类产品死在这

✓ 正确做法：时间纯函数任意时刻可重算，无状态
// 金额 = f(now)，每帧重算，不做累加
// 返回双账：paid 进月薪，shadow 只做对照
function ledgerAt(now: EpochMs): Ledger {
  const s    = payableSeconds(cfg.clockInAt, now);
  const base = clamp(s, 0, cfg.dailySec);
  const ot   = max(0, s - cfg.dailySec);
  const unit = cfg.perSec * ot;

  const paid = cfg.perSec * base
    + (cfg.otMode === 'paid'
        ? unit * cfg.rate        // 计费：真给
        : 0);                    // 不计：主账封顶

  const shadow = cfg.otMode === 'unpaid'
    ? unit * cfg.legalRate       // 1.5 / 2 / 3，只算不收
    : 0;

  return { paid, shadow };      // 两个字段，永不合并
}

// 午休加班是另一条路径：主账纹丝不动，只折白干
function lunchShadow(spans: Span[], cfg): Milli {
  return spans.reduce((sum, sp) => {
    // 封顶到 13:30：过了这个点，人已经在正常工作时间里
    const end = Math.min(sp.end, cfg.lunchEnd);
    return sum + (end - sp.start) / 1000
               * cfg.perSec * 1;   // 固定 1×，午休本无加班费
  }, 0);
}

// payableSeconds 内部扣除：午休、请假、暂停区间
四条硬约束：①金额全程用整数「毫」（1 元 = 1000 毫）存储与运算，只在渲染时转成小数，彻底规避浮点误差； ②所有时间运算走 epoch 毫秒，不碰本地时间字符串，天然规避夏令时与时区跳变； ③渲染节流到 10 Hz，但不是「每 10Hz 加一次」，而是「每 10Hz 重算一次」——这两者结果完全不同； ④shadow 只写不读——它可以被展示、被单独统计，但任何计算路径都不得读取它去影响 paid。
02-C′计薪天数与工作制：两个数不是一回事
结论先说：有关联，但关联方式是「工作制决定 21.75 能不能用」，而不是「工作制改变 21.75 的值」。 21.75 永远是 21.75，它只回答一个问题——我的日薪是多少。加班怎么算、算不算加班，是工作制回答的。 把这两件事混在一起，就会出现「时薪算对了、加班费算错了」的情况。

为什么 21.75 不变，20.67 却变了

法定节假日有个特殊性质：不上班，但照发工资（劳动法第五十一条）。所以它进不进公式，取决于这个公式在数什么：

· 数「谁发钱」 → 13 天节假日要算进去 → 只减 104 天休息日 → 21.75 不变

· 数「谁上班」 → 13 天节假日不上班 → 要减掉 → 20.83 → 20.67

2024 年 11 月国务院令第 795 号把春节、劳动节各加 1 天（11 → 13 天），只动了后一个数。 人社部发〔2025〕2 号同时废止了 2008 年的旧文件，所以「20.83」这个数字今天已经作废。

所以本产品有一条必须写进说明书的前提：它只对「标准工时制 + 双休或固定排班」的工作日成立。 另外三类工时制度的用户，日薪依然算得对（21.75 全国统一），但加班那一栏是错的—— 综合工时按月看是「这个月总共超了多少小时」，不是「今天下班后多坐了两小时」。 而即使在标准工时制下，加班倍率也只实现工作日 1.5× 这一档，休息日与法定节假日不单独区分。
这不是缺陷，是范围：把「今天赚了多少」做准，比覆盖所有工时制度更值钱。但边界要写在明处，不能让用户以为算的是法定加班费。
边界 1
7.5 小时不是法定值
界面上凡出现 7.5，都要标明「你的作息」。否则用户会拿它当法定小时工资去和 HR 争论，一争就露馅。
边界 2
单休本身已经超时
周 6 天 = 每周 48 小时，超过标准工时的 40 小时。法律上要么是加班（应付 2× 或补休），要么单位申请了综合工时。产品不该把它当成和双休平等的选项，选它时要提示。
边界 3
模型不认「今天是什么日子」
统一按工作日算：日薪基线、9:00 起算、18:00 封顶。休息日没有「下班」节点，也就没法按 2× 计。 所以已定不做三档费率，改为休息日自动暂停——不给数字，比给一个错的数字好。

05-C平台差异清单

Windows 11 x64 / arm64

  • WebView2 运行时：Win11 自带；Win10 需检测并引导安装（或打包固定版本，+80MB）
  • 透明窗口：依赖 WS_EX_LAYERED，Tauri 已封装；注意 DWM 合成开启时才有真透明
  • 高 DPI：125%/150% 缩放下要按 devicePixelRatio 校准圆角与模糊，否则边缘发毛
  • 置顶失效：全屏游戏/UWP 应用可能抢置顶，需定时校正（不做则用户以为坏了）
  • 未签名 exe：会触发 SmartScreen「Windows 已保护你的电脑」。已定不买证书——用 SHA256 校验 + 安装页三步引导绕过（见 05-C′）
  • 自启：写 HKCU\...\Run 或任务计划，避免 UAC 弹窗

macOS 13+ arm64 / x64（Universal）

  • 无签名无公证：Gatekeeper 会拦死，双击报「已损坏，应移到废纸篓」——这句报错会劝退九成用户。已定不买 Apple 开发者账号，靠「右键 → 打开」或一行解隔离命令（见 05-C′）
  • 菜单栏应用：LSUIElement = true 隐藏 Dock 图标，只留菜单栏
  • 全屏空间：需 canJoinAllSpaces + fullScreenAuxiliary，否则切到全屏 IDE 就看不见了
  • 圆角与阴影：isOpaque = false + backgroundColor = .clear，阴影必须自绘
  • 辅助功能权限：只有用到「检测键鼠活动」时才需要，能不用就不用，省一次授权摩擦
  • Apple Silicon：打 Universal 包，别只出 x64 让 Rosetta 兜底
05-C′免签名分发：不买证书之后，用户怎么装得上
这是本项目最大的转化损耗，必须当成功能做，不能当成一句文档。 不买证书省了 ¥2000 + $99，但代价全落在第一次安装上—— 而且两端严重程度完全不同：Windows 只是吓唬，macOS 是真的打不开。
WindowsSmartScreen · 可绕过 · 损耗中等
用户双击 exe，弹出蓝色的「Windows 已保护你的电脑」。这个弹窗默认按钮是「不运行」， 而且要点「更多信息」才会露出「仍要运行」——大多数人走到这就不走了。
对策三条，按成本排：
① 安装页第一屏就放这个弹窗的实拍截图，用红框标出「更多信息 → 仍要运行」
② 提供 .zip 免安装版（解压即用），绕开 exe 的 Mark-of-the-Web 概率更高
③ 官网放 sha256，让用户能自己核对包没被动过
macOSGatekeeper · 报错文案吓人 · 损耗极高
双击会报 「『牛马薪动了』已损坏，无法打开。你应该将它移到废纸篓。」 ——注意它说的是已损坏，不是「未验证开发者」。用户会真的以为文件下坏了，直接删掉重下，重下三次还是这句。
唯一可靠的两条路：
① 右键 → 打开 → 弹窗里点「打开」（只需一次，之后正常双击）。这个动作很多人不知道
② 终端一行：xattr -dr com.apple.quarantine /Applications/牛马薪动了.app
安装页要给可一键复制的按钮，而不是让人手打这行命令
安装页要长什么样（这页比落地页更重要）
第 1 屏不介绍功能，先解决「怎么装」。按平台自动分栏，每栏三步，每步一张实拍截图： 下载 → 绕过系统拦截（贴图 + 复制按钮）→ 首次启动配置薪资。
底下固定一行校验区：版本号 · 文件大小 · SHA256 前 16 位，并写一句 「我们没买代码签名证书，所以系统会警告；你可以用上面的 SHA256 核对文件是否被篡改」—— 把没钱这件事讲成坦诚，而不是装作没发生。这比一张假证书更能换信任。
连带：自动更新也必须自己校验签名。没有系统级签名兜底，清单里的 sha256 就是唯一防线—— 下载完先算哈希，对不上直接删包、不执行、并提示「本次更新校验失败，已保留旧版本」。
什么时候该回头买证书：当「安装失败」的反馈占到问题总数两成以上，或者出现第一个真实的病毒误报投诉。 那时花 ¥2000 + $99 是买转化率，不再是买安心。现在不买是合理的——但要把这笔账记在这儿，别到时候以为是新问题。

05-E自动更新服务（服务端要点）

检查更新看着是一个按钮，实际上是一条完整的发布链路：客户端只负责问，服务端负责回答得可信。 这一节把服务端必须做到的事列清楚——少做任何一条，都会变成「推了一个装不上的包」或者「推了一个不该推的包」。

05-E1客户端状态机（对应「设置 · 关于」里那个按钮）
idle → checking → latest ／ available → downloading → verifying → ready → restart 失败 → failed（退避重试，不打扰）
服务端只需维护三样东西
  • 一份静态清单（manifest.json，按通道 / 平台 / 架构分文件）
  • 一堆签好名的安装包（放对象存储，走 CDN）
  • 一个灰度百分比（改一个数字就能全量或刹车）
没有用户表、没有数据库、没有登录态、也没有授权校验和付费闸门——产品免费开源，「检查更新」只回答「有没有新版本」这一个问题。 能做成纯静态就别做接口—— 这类请求一天只有几万次，但一旦挂掉，用户会以为是自己的网有问题。
客户端检查时机
  • 启动后 30 秒静默检查一次（避开启动高峰，不拖慢冷启动）
  • 之后每 24 小时一次，用单调时钟计时，不信系统时间
  • 切回前台时若距上次 > 24h，补一次
  • 手动检查强制绕过缓存（带 Cache-Control: no-cache）
  • 自动检查失败静默；手动检查失败必须给结果

四个字段决定成败

sha256　下载完必须全量校验。只信 HTTPS 不够——CDN 回源错误、企业代理插证书，都会让你装上一个坏包。

sig　Ed25519 签名，公钥硬编码在客户端里。私钥泄露等于可以给所有用户推任意程序，所以私钥离线保管、只在发版机上出现。

rollout.percent　灰度开关。客户端用 hash(device_hash + salt) % 100 < percent 判断自己是否该看到这个版本。出问题把它改成 0，一分钟内止血，不用发版。

force_below　核按钮。低于该版本只给「立即更新」，没有「稍后」。只在安全事件时动，动了就要在公众号同步说明。

05-E3服务端能力清单（逐条可验收）
能力具体要求不做会怎样
清单托管静态 JSON 放对象存储 + CDN，Cache-Control: max-age=300，带 ETag做成动态接口，发版当天必被重试打穿；改缓存要等 CDN 回源
产物分发每平台每架构独立包（win-x64 / win-arm64 / mac-arm64 / mac-x64），必须支持 Range 请求断点续传失效，10 MB 包在弱网下重下 3 次，用户直接放弃
下载地址清单里放不带凭据的 CDN 域名；如需防盗链，用 302 + 5 分钟 TTL 的签名 URL永久 URL 被爬走当成免费下载站，流量账单自己扛
签名校验私钥离线，公钥进客户端；签名覆盖 version+platform+arch+sha256只校验 HTTPS 等于没校验，中间人可替换清单
代码签名不做（已定不买证书）。改为：清单里带 sha256，客户端下载后本地校验，不一致直接拒装并向清单服务上报没有系统级签名，用户得手动绕过 SmartScreen / Gatekeeper——这是本项目最大的转化损耗，只能靠文档与校验补齐信任
灰度发布percent + salt 稳定分组；同设备每次看到的结果一致，不会反复横跳全量直推，一个崩溃 bug 就是 100% 用户受影响
回滚保留上一版本安装包；数据库迁移只加列不删列，降级仍能读回滚时旧版本读不了新库，用户数据直接「消失」
版本比较语义化版本逐段比较（1.10.0 > 1.9.0），不比字符串字符串比较会让 1.10 排在 1.9 前面，用户永远收不到更新

手动检查的意义不是「更快拿到更新」，是让用户确认这个按钮是活的。 所以它必须有可见的过程（解析 → 拉清单 → 验签 → 比版本），而不是转一圈然后什么都不说。
发布流水线（6 步，可脚本化）
01　构建双端产物（CI，win + mac 两个 runner）
02　代码签名 / macOS notarize，签名失败即中止
03　算 sha256、生成差分包、上传对象存储
04　生成 manifest，离线机签名，回传覆盖
05　灰度 percent=10，观察 24h 的崩溃率与更新成功率

第 4 步是关键：签名动作必须离线，不能放在能联网的 CI 里，否则私钥等于挂在公网上。
四个必须提前想清楚的坑： ①升级不能动用户的库——迁移脚本要幂等，且旧版本必须仍能读新库，否则回滚 = 数据丢失； ②时钟回拨——用户改系统时间会让「24h 一次」失效或疯狂重试，用单调时钟 + 服务端 Date 头校正； ③差分包只对相邻版本有效——跨越多个版本时回落到全量包，别为了省 8 MB 换来 3% 的失败率； ④「稍后」要能记住——用户点了稍后，就别在这次会话里再弹第二次，否则就是骚扰。
05-F开源策略：开源外壳，闭源引擎

分界线划在这儿的理由：能被人抄走做出一个「长得一样」的产品的，是 UI；抄了才真正有威胁的，是 算法与口径。 而反过来，UI 开源的价值最高（皮肤、翻译、issue 都在这儿），引擎闭源的损失最小（用户看不见它）。 这条线正好和 Tauri 的进程边界重合——引擎在 Rust 侧，前端只是渲染器。
05-F1为什么不靠前端混淆
JS 混淆是纸门

Tauri 的前端跑在 WebView 里。开发构建一个 Ctrl+U 就能看源码；发行构建虽然打包进资源，但资源包本身就是个压缩文件，解开是常规操作。

混淆只能把「5 分钟看懂」变成「1 小时看懂」，而看懂之后仍然是那三行公式。对算法保护来说，这等于没做。

Rust 侧才是真的「不在那一侧」

引擎编进原生库，前端通过 IPC 只拿到 结果：{ paid, shadow, ot }。公式、常数 21.75、1.5×、区间封顶逻辑全都不在可打开的那一侧。

这不是「藏起来」，而是让它根本不存在于用户能读的地方——比任何加密壳都硬。

必须承认的事实：本地校验没有不可破解的。只要程序在用户机器上跑，补一个 jmp 就能绕过。 所以这里的目标不是「无法破解」，而是让破解成本高于自己重写的成本—— calcOf 三行公式，重写只要一小时，加再多壳也拦不住想重写的人。 真正留住用户的是迭代速度、文案库、和那份「代码可查」的信任，壳只负责让「原样打包上架」这条路走不通。
05-F2a加固落在哪：冷路径做绝，热路径放过

加固档已定。但整程序平坦化是错的做法——不是怕慢，是怕没用。

黑盒调用绕过一切壳。攻击者根本不需要读你的代码：import 动态库，喂 1000 组 (sec, state) 看返回值，就能拟合出公式—— 这比逆向快得多。calcOf 每帧被调用几十次，谁都能量它。对它做控制流平坦化，等于给一扇敞开的门上了把好锁。

真正值得加固的是读不出、也测不出的东西：影子账的区间合并规则、午休封顶、跨零点封账、年终奖摊算口径。 这些逻辑分支多、与状态相关，黑盒测试要构造几十种时间组合才能逼近，静态分析反而更省力——加固的收益正好落在这一侧。

05-F2b四件事，按这个顺序做
① 编译参数（半小时，双端都安全）
# paypulse-core/Cargo.toml
[profile.release]
lto           = "fat"   # 跨 crate 内联，符号边界消失
codegen-units = 1       # 全量优化，顺带减少可见符号

注意：panic="abort" 会让崩溃堆栈变得不可读。所以它只用在引擎 crate， 主程序保留 unwind——否则 06-B 的崩溃收集会形同虚设。
② 常量外置（半天，收益最高）

字符串用 obfstr 这类 crate 编译期加密，运行时逐字节解密，.rodata 里不留明文。

数值的正确做法不是「藏」，是让它不存在：21.75、1.5、8000 全部作为 Params 字段从主程序传入， 引擎不持有任何默认值——连 unwrap_or(21.75) 这种兜底都会把常量带回来。

这一步性价比最高：成本半天，且产品上本来就更对——用户能改计薪日与倍率，写死反而错。

③ 控制流平坦化（1–2 周，只对冷路径）

Rust 没有现成的 ollvm。可行路径是自己接一段： --emit=llvm-ir → 跑 LLVM Flattening pass → llc 回目标文件 → link。

只能对 paypulse-core 单独走这条构建链，不能污染主仓 CI——主仓是全开源的，构建脚本里出现混淆步骤会很怪。

真实成本：每次 rustc 大版本升级要跟一次 pass 兼容性。这是持续性成本，不是一次性投入。

④ 运行时壳（Windows 可选，默认关）

VMProtect / Themida 能把二进制进一步压成"看不懂的虚拟机字节码"，但有两个硬冲突：

与 06-C 的杀软误报直接冲突——这类壳本身就是杀软的重点特征库目标，装上之后误报率会明显上升。

macOS 用不了：自修改代码违反 hardened runtime，公证后 Gatekeeper 直接拒绝启动。

两个反直觉的发现，直接改掉了原来的写法：
①from_bits 是 const fn，编译期就求值成同一个 f64。实测两个二进制里 21.75 都落在 0x3A818、1.5 都在 0x3A820，紧挨着躺在常量池里——换了个写法，字节一个没变，省下的只是源码观感。
②编译器会把你没防备的常量折叠掉，反而把想藏的留下。8000 在 ①② 里根本找不到（早被折进 per_sec = 0.0136…）， 却在 ③ 里出现了——因为 black_box 阻断了折叠。你以为在藏东西，其实是在暴露哪几个数字重要。
所以「加固档」的重心整体挪了一格：常量这一层不靠混淆，靠外置——引擎只认 Params，不认 21.75。 混淆留给真正测不出来的东西：区间合并、窗口封顶、跨零点封账（见 05-F2a）。 这也解释了为什么 lib.rs 里一个业务数值都搜不到，却仍然值得做第 ③ 步。
加固档的两条硬约束，写进 CI 里： ①macOS 一律不用运行时壳，只做编译期混淆——Apple 公证会拒； ②平坦化只作用于冷路径，CI 里加一条断言：热路径符号必须保持未平坦化，且 calcOf 的 P99 耗时 < 1ms。 另有一条副作用要提前接住：加固后的崩溃堆栈基本不可读，所以每次发版必须留一份带符号表的构建产物在私有存储里，只用来还原崩溃，不随包分发。
05-F3为什么选 AGPL-3.0 而不是 MIT
AGPL-3.0 正好堵住那个口子

MIT 之下，任何人可以拿你的代码闭源、改名、上架收费——你开源的心血变成别人的商品。这正是你要防的事。

AGPL 的规则是：你可以随便用、随便改、随便商用，但改了必须同样开源，并且通过网络提供服务也算分发。「拿了闭源卖钱」这条路在法律上直接封死——不用技术手段，用许可证就够了。

已知的副作用

部分公司会禁止员工使用 AGPL 软件，法务口径保守。对一个装在个人电脑上的薪资小工具，影响远小于对基础库。

更体面的备选是 BSL 1.1：源码公开可读，约定年限内禁止商用，到期自动转 Apache-2.0。若之后想做企业版，这个更平滑。

开源换来的东西（不是情怀，是实打实的省事）： ①节假日数据——中国调休每年变，社区 PR 比一个人维护准得多，这是最容易烂的一块数据； ②机型适配——mac 的缩放比、多屏、外接显示器组合千奇百怪，只有用的人多才会被发现； ③信任——一个要读你工资的程序，「代码可查」比任何「我们不收集数据」的文案都硬。 红线一条：任何工资数据、截图、本地库文件都不许进仓库，issue 模板第一行就拦截图。
分仓的真实代价，先说清：引擎一改就要双仓联调、ABI 要版本化、CI 要跨仓取产物、发版要两个 tag 对齐。 一个人开发时这是实打实的摩擦。如果哪天觉得重了，退化方案是：全仓开源 AGPL + 只留基础档裁剪， 把保护完全交给许可证——法律手段其实比技术手段更耐用，只是拦不住不看许可证的人。

决策 1
技术栈：Tauri 2
双端一套代码，Rust 只负责窗口层与计薪引擎。包体 10MB、内存 60MB 是这个产品的入场券——一个薪资小工具占用超过微信，用户会直接卸载。
回退成本：05-A/B/C 三节重写；改 Electron 则安装包 10MB→150MB、内存 60→250MB，M0 的 PoC 全部作废重做。
决策 2
调性：双模式
默认情绪向（截图这套：自嘲、等价物换算），设置里可一键切严谨模式（只报数字，不评价）。 传播靠前者，长期留存靠后者——一份产品吃两类人。
回退成本：文案库要做两套（约 120 条），每条都得有「严谨版」；通知、气泡、空状态、异常提示全部翻倍。这是本方案里最费工的一项决定。
决策 3
分发：免费开源，引擎闭源
主仓上 GitHub，AGPL-3.0；计薪引擎留在私有仓，以原生库形式随包发行。无账号、无授权校验、无付费闸门——「检查更新」退化为纯版本比较。 加固档已定：冷路径做控制流平坦化，热路径只做常量拆解与字符串加密（分界见 05-F2a）。
回退成本：若改付费，必须引入授权与支付，与「不做账号」直接冲突，05-F、隐私页、检查更新三处都要重写。详见 05-F。
决策 4
裁剪：云同步 / 导出 / 分享卡全不做
三者全砍。代价已经写在引导页和隐私页里，不藏在协议里：换电脑重配约 90 秒，历史不跟过去。
换来的是：没有账号体系，就没有任何一环能要求你登录，「不联网」这句话才站得住。
决策 5
加班倍率只做一档（1.5×），不做三档
法定是三档：工作日 1.5×、休息日 2×、法定节假日 3×。做三档的门槛不是那张节假日表（日历本来就有，见「作息与工作日」）， 而是「今天是什么日子」根本不在计薪模型里——现在所有天都按工作日算， 有日薪基线、9:00 起算、18:00 封顶。休息日没有「下班」节点，要支持 2× 就得让整个状态机按日子类型分叉， 属模型级改动。已定不做，统一 1.5×，措辞降级为「折算价值」而非「法定应得」。
连带换来的一个小功能：既然模型不认休息日，休息日打开它会虚增 367.82——所以加了休息日自动暂停， 用已有日历判断，不给数字。这比多算一档倍率更值：宁可少算，不能虚增。
回退成本：要上三档，得先给引擎加「日子类型」入参、改状态机分叉、改 02-A' 两张卡与 02-D 两行， 并重跑影子账所有区间用例；约一周，且引擎 ABI 要升版本。
决策 6
身份与分发：com.bydota.paypulse · paypulse · 不买证书
包标识符 com.bydota.paypulse（Tauri identifier / macOS bundle id）； 英文名与仓库名保留 paypulse / paypulse-core，中文品牌「牛马薪动了！」只做显示名。 签名证书一律不买——Windows OV（约 ¥2000/年）与 Apple Developer（$99/年）都不申请。
为什么标识符要现在定：它绑着系统通知权限、开机自启、更新签名、用户数据目录。上线后再改等于换一个 App，老用户的数据不跟过去、权限要重授。
不买证书的代价（已写进 05-C′）：macOS 双击会报「已损坏，应移到废纸篓」——不是警告，是打不开；Windows 弹 SmartScreen，默认按钮还是「不运行」。 对策是把安装引导当功能做：实拍截图 + xattr 一键复制 + SHA256 校验区。
回头买的条件：「装不上」的反馈占到两成以上，或出现第一个真实误报投诉。那时这笔钱是买转化率，不是买安心。
